Install-time code

Packages whose lockfile entry says an install step runs code on the machine that installs them (npm hasInstallScript). This is not a vulnerability: many are native modules being built. It is also how a malicious package runs, so look at the ones you do not expect. A lockfile that cannot say is named in the notes at the top.

Runtime products (PHP, nginx, ...)

What the application runs on, from the latest scan-runtime: whether the release line is still supported and on its newest patch, and, when NVD was asked, the CVEs it lists for that exact version. Release lines, not a scan of libraries.

AI assistant configuration

What the latest scan-agent-config found in the files that steer an AI coding assistant: rule files, MCP server settings, hooks, auto-run tasks and skills (their text, scripts and dependencies). Rule findings are suspected patterns to confirm; advisory findings come from published data about the packages an MCP server or a skill starts or lists. The text that matched is never kept.

Suspected issues in your own code

Pattern matches from the built-in rules (and gitleaks/semgrep when requested). These are leads to confirm, not proven vulnerabilities.
  • Data: OSV, NVD, CISA KEV, EPSS, OpenSSF Malicious Packages (through OSV), MITRE CWE, OWASP MCP Top 10 and OWASP LLM Top 10 (the basis of the assistant-configuration rules), OWASP CI/CD Top 10 and GitHub Security Lab (the basis of the workflow rules); for runtime products endoflife.date and php.net.
  • A clean result means no known advisory matched the lockfile versions; it does not prove the code is secure.
